# Posterior Unification Plan — 29-Apr-26

**Status**: Design plan for an in-flight refactor.
**Author target**: senior engineer executing the plan from this document.

## 1. Goal

`edge.p.posterior` becomes the L1.5 promoted Beta-shape surface — source-agnostic, written exclusively by `applyPromotion` from `model_vars[promoted].probability`, mirroring how `applyPromotion` already writes the promoted scalar surface (`p.forecast.{mean, stdev, source}`) and the promoted latency surface (`p.latency.{mu, sigma, promoted_t95, promoted_onset_*, ...}`). Bayesian-fit-specific metadata (MCMC diagnostics, fit identity, LOO/PPC, prior tier) leaves `p.posterior` and lives instead on the bayesian source entry. After the change, `model_vars[bayesian].probability` carries the full Beta shape on the same footing as `model_vars[analytic].probability`, and the BE rate resolver reads the promoted `p.posterior` unambiguously without needing source-conditional fallback logic. The `switch-registered → switch-success` parity defect — FE 0.6715 from analytic, BE 0.8513 from a stale bayesian Beta on `p.posterior` — disappears as a structural impossibility because the promoted source determines what is on `p.posterior`.

## 2. Current shape (brief)

`bayesPatchService.applyPatch` is the de facto only writer of the full Beta shape onto the live edge: at `bayesPatchService.ts:314-378` it projects the window slice onto `p.posterior` together with bayesian-fit diagnostics (`ess`, `rhat`, `divergences`, `evidence_grade`, `fitted_at`, `fingerprint`, `provenance`, `prior_tier`, `delta_elpd`, `pareto_k_max`, `n_loo_obs`, `ppc_*`); at `:383-431` it projects the latency-posterior block onto `p.latency.posterior`; at `:435-496` it builds a slim `model_vars[bayesian]` entry that carries `{mean, stdev}` only on `probability`; at `:498-499` it upserts and calls `applyPromotion`. The UpdateManager mapping at `mappingConfigurations.ts:799-817` cascades the same projection from the parameter file. `posteriorSliceContexting.contextProbabilityBlock` (`:59-130`) re-projects on `currentDSL` change and `syncBayesianAndPromote` (`:219-281`) rebuilds a slim bayesian `model_vars` entry from the projected `p.posterior` before promotion. CF apply (`conditionedForecastService.applyConditionedForecastToGraph`) writes only L4/L5 — never `p.posterior`. The BE resolver (`model_resolver.resolve_model_params`) reads `posterior_block.{cohort_alpha, cohort_beta, alpha, beta, alpha_pred, beta_pred, window_n_effective, cohort_n_effective}` first, then falls through to `model_vars[promoted_source].probability.{...}` (`model_resolver.py:233-531`). The same pattern recurs in `cohort_forecast.py:237-276`, `forecast_runtime.py:1097-1134`, `span_adapter.py:61-117`, `api_handlers.py:2802-2921`.

The plan's audit covers both the TypeScript and Python codebases. TypeScript-side findings are concentrated in `graph-editor/src/`. Python-side findings span `graph-editor/lib/runner/` (rate resolver, span adapter, forecast runtime, cohort forecast v1 and v2), `graph-editor/lib/api_handlers.py` (path-overlay computations), `graph-editor/lib/graph_types.py` (Pydantic schema for `model_vars`), and `bayes/` (slice/inference layer; see §6.5.1). The Python audit found no consumers of bayesian-only posterior metadata on graph edges, which is the load-bearing safety check for Step 1's schema trim.

The asymmetry between the two branches of the resolver (read full Beta from `p.posterior` vs read full Beta from `model_vars[analytic].probability`) is the surface where the parity defect manifests when `model_source_preference = 'analytic'` but a stale bayesian fit still sits on `p.posterior`.

## 3. Target shape

After the refactor, every named field on the live graph maps to one and only one writer, and the writer is correct for the field's semantics.

The **source ledger** (`p.model_vars[]`) carries one entry per source. Each entry's `probability` block carries the full aggregate Beta shape: `{mean, stdev, alpha, beta, n_effective, provenance, cohort_alpha, cohort_beta, cohort_n_effective, cohort_provenance}` plus, for sources that emit a predictive flavour, `{alpha_pred, beta_pred, cohort_alpha_pred, cohort_beta_pred}`. Today this is true for `model_vars[analytic]` (after 73b Stage 2). After this refactor it is also true for `model_vars[bayesian]` — projected from `posterior.slices['window()']` and `posterior.slices['cohort()']` by the bayes patch writer and by the slice-contexting helper. Writers are: FE topo Step 1 for analytic; bayes patch + slice contexting for bayesian.

Bayesian-fit-only metadata moves onto a sibling block on the bayesian source entry. The plan adds `model_vars[bayesian].fit_diagnostics` carrying `{ess, rhat, divergences, evidence_grade, gate_passed, fitted_at, fingerprint, provenance, prior_tier, surprise_z, hdi_lower, hdi_upper, hdi_level, hdi_lower_pred, hdi_upper_pred, cohort_hdi_lower, cohort_hdi_upper, cohort_hdi_lower_pred, cohort_hdi_upper_pred, delta_elpd, pareto_k_max, n_loo_obs, ppc_coverage_90, ppc_n_obs, ppc_traj_coverage_90, ppc_traj_n_obs}`. Ess/rhat/divergences/evidence_grade/gate_passed are already on `quality`; the existing `quality` is preserved as the gate input and `fit_diagnostics` extends it with the rest of the bayesian metadata — they sit alongside on the same entry rather than collapsing, because `quality` participates in promotion gating and is referenced from BE Python (`graph_types.ModelVarsQuality`). The simplest discipline is: `quality` stays as-is, and a new optional `fit_diagnostics` field captures everything else that was on `p.posterior` and is bayes-only. HDI fields are listed under fit diagnostics rather than under generic Beta because today they are computed by the MCMC quantile path, not from α/β closed form; the plan note in §9 covers the option of computing them lazily from α/β at display time.

The **selector layer** (L1.5) is unchanged: `model_source_preference` and `model_source_preference_overridden`.

The **promoted scalar surface** (L2 narrow) is unchanged: `p.forecast.{mean, stdev, source}` and the promoted latency block `p.latency.{mu, sigma, promoted_t95, promoted_onset_delta_days, promoted_mu_sd, promoted_sigma_sd, promoted_onset_sd, promoted_onset_mu_corr, promoted_path_t95, promoted_path_mu_sd, promoted_path_sigma_sd, promoted_path_onset_sd, promoted_path_mu_sd_pred}`.

The **promoted Beta surface** (new, L1.5) lives at `p.posterior` and carries source-agnostic Beta-shape fields only: `{distribution: 'beta', alpha, beta, n_effective, provenance, cohort_alpha, cohort_beta, cohort_n_effective, cohort_provenance, alpha_pred, beta_pred, cohort_alpha_pred, cohort_beta_pred, window_n_effective}`. The HDI fields (`hdi_lower`, `hdi_upper`, `hdi_level`, `cohort_hdi_*`, `*_hdi_lower_pred`, `*_hdi_upper_pred`) move to `fit_diagnostics` initially because they are written today only when bayesian. A future improvement can re-introduce them on `p.posterior` as closed-form derivations from the promoted α/β; that is out of scope for this plan but called out in §9.

The **promoted latency posterior surface** at `p.latency.posterior` follows the same rule: it becomes the source-agnostic projection of `model_vars[promoted].latency` and is written by `applyPromotion`. The `model_vars[bayesian].latency` block already carries the lognormal-posterior parameter values that `p.latency.posterior` exposes — they are just under shorter names. The patch writer at `bayesPatchService.ts:461-487` stores `windowSlice.mu_mean` as `latency.mu`, `sigma_mean` as `latency.sigma`, and `onset_mean` as `latency.onset_delta_days`; the cohort variants land as `path_mu`, `path_sigma`, `path_onset_delta_days`. Promotion projects these to `p.latency.posterior.{mu_mean, sigma_mean, onset_delta_days, path_mu_mean, path_sigma_mean, path_onset_delta_days}` by simple rename, with the dispersion SDs (mu_sd, mu_sd_pred, sigma_sd, onset_sd, onset_mu_corr, path_*) passing through unchanged. Bayesian-only metadata (ess/rhat/fitted_at/fingerprint/provenance for the latency posterior, plus PPC and LOO fields specific to the latency fit, plus HDI fields `hdi_t95_lower/upper`, `path_hdi_t95_lower/upper`, `hdi_level`) moves under `model_vars[bayesian].fit_diagnostics`. Today, analytic does not produce a populated `p.latency.posterior` — promotion will write nothing in that case, leaving the field unset. This matches existing behaviour with `analytic` promoted.

The single-writer principle for `p.latency.posterior` is firm: **`applyPromotion` is the only writer**, projecting from the active `model_vars[*].latency` entry. There is no "for now" exception. The slice-contexting helper writes into `model_vars[bayesian].latency` and lets promotion handle the surface — same pattern as the probability surface.

`p.posterior` and `p.latency.posterior` are recomputed by `applyPromotion` on every promotion-triggering event, exactly like `p.forecast.{mean, stdev, source}` and the promoted latency scalars are today. They never persist a different source's shape than the active selector dictates. Stale-bayes-on-analytic-pin becomes structurally impossible — provided every relevant event actually runs `applyPromotion`. §4 Step 0 covers the promotion-coverage prerequisites that have to hold for that "provided" clause to be true; without those gaps closed first, the refactor does not deliver the bug fix.

## 4. Step-by-step migration plan

This plan can be executed atomically (single PR) or phased (three commits). Phasing reasoning is given at the end of this section.

### Step 0 — Promotion coverage prerequisites (must land before Step 2)

The new architectural invariant is "**`p.posterior` reflects the active selector after every event that mutates `model_vars` or `model_source_preference`**". That invariant only holds if every such event ends with `applyPromotion`. An audit of the current code base identifies six sites where a mutation is not paired with promotion. Each one is either an outright gap (no promotion ever runs in that path) or an implicit caller contract (the call site relies on a downstream consumer to promote). Both forms must be made explicit before Step 2 lands, otherwise the refactor cannot deliver the parity-defect fix in those paths.

Verified gaps:

The first gap is at `bayesPriorService.ts:232-260` (`resetPriorsForAllParams`). After the param-file flag flip, the function walks the live graph in-place at `:234-249`, fails the `model_vars[bayesian].quality.gate_passed` flag, deletes `model_source_preference` and `model_source_preference_overridden` from each edge, and at `:253-255` may flip the graph-level `model_source_preference` from `'bayesian'` to `'best_available'`. No `applyPromotion` runs. The comment at `:223-230` records the contract: the caller is expected to immediately trigger a from-file fetch that runs the FE pipeline and promotes. This works when the caller is the Data Menu's "Reset all priors" action because that does trigger a fetch, but the contract is fragile and undocumented for any other future caller. The fix is to add an explicit promotion sweep over the graph's edges at the end of the function, with the documented invariant that `resetPriorsForAllParams` leaves the graph in a fully promoted state. The fix is small and idempotent with the downstream fetch.

The second gap is at `bayesPriorService.ts:303-339` (`deleteHistoryForAllParams`). The same pattern — bulk param-file deletion followed by in-place graph mutation that fails gates, deletes edge-level pins, and additionally deletes `edge.p.posterior`, `edge.p._posteriorSlices`, and `edge.p.latency.posterior` at `:330-332`. After the refactor, deleting `p.posterior` directly is fine because the next promotion will rewrite it; but the function does not run that promotion. The same fix applies: add an explicit promotion sweep.

The third gap is at `bayesPriorService.ts:34-65, 112` (`invalidateBayesianOnEdges`, called from `resetPriorsForParam`). Single-param variant of the bulk flow: deletes the edge-level pin, fails the bayesian gate, and (when `clearPosterior` is set) deletes `p.posterior`. Again, no `applyPromotion`. The single-param caller (BayesPosteriorCard "reset prior" button) does trigger a fetch downstream, but the same fragility argument applies. Fix: have `invalidateBayesianOnEdges` run promotion on each edge it touches.

The fourth gap is at `dataOperations/fileToGraphSync.ts:2027-2028` (latency-only update branch). When a parameter file's latency changes but its probability does not, the function mutates `p.model_vars[idx] = { ...p.model_vars[idx], latency: mergedLatency }` in place at `:2028` and does not call `applyPromotion`. The probability-and-latency branch immediately above at `:2001-2002` does promote correctly. The asymmetry is unintentional and means a parameter-file edit that affects only dispersion fields leaves `p.forecast.*` and the promoted latency scalars stale. Fix: add `applyPromotion(...)` after `:2028`.

The fifth site is at `fetchDataService.ts:2151` (FE horizon bootstrap, `upsertModelVars(ep, analyticEntry)`). This sits inside the same fetch that subsequently runs the LAG/FE pass at `:2183` and a downstream `applyPromotion` sweep around `:2297-2344`. So in current code the bootstrap is always followed by promotion within the same fetch. This is not an outright gap, but it is an implicit contract. After the refactor, if any future caller of the bootstrap path skips the LAG/FE pass, `p.forecast.*` will be stale. Fix: make the call ordering explicit by adding a comment at `:2151` recording the dependency, and add an integration test that inserts a latency-only bootstrap mid-pipeline and asserts post-pipeline promotion correctness.

The sixth site is at `posteriorSliceContexting.ts` (any path that mutates `model_vars[bayesian]` outside `syncBayesianAndPromote`). Today, `contextProbabilityBlock` writes `p.posterior` directly and `syncBayesianAndPromote` runs promotion. After Step 5 reverses the data flow (slice → `model_vars[bayesian]` → promotion), every contexting code path must end through `syncBayesianAndPromote`. The plan's Step 5 already addresses this, but Step 0's audit confirms there are no other contexting paths today that would need updating.

Acceptance criterion for Step 0: every site that currently calls `upsertModelVars`, deletes a `model_vars` entry, edits `model_vars[X].quality`, or sets/deletes `model_source_preference` or `model_source_preference_overridden` is paired with `applyPromotion` either inline or through an unbroken caller chain that always promotes. A test pin (`promotionCoverageInvariant.test.ts`, new) walks the call graph for these mutations and asserts the pairing for every code path. Without this acceptance criterion met, Step 2 is unsafe.

Estimated effort: small. Two functions in `bayesPriorService.ts` gain a promotion sweep. One branch in `fileToGraphSync.ts` gains a single line. One comment elsewhere. One new test.

### Step 2 — Extend `applyPromotion` to write the promoted Beta and latency posterior surfaces

Extend `modelVarsResolution.PromotionResult` at `:86-109` to carry an optional `posterior` block reflecting the resolved entry's Beta shape and an optional `latency_posterior` block reflecting the resolved entry's latency posterior. `promoteModelVars` populates these from `entry.probability.{alpha, beta, n_effective, provenance, cohort_alpha, cohort_beta, cohort_n_effective, cohort_provenance, alpha_pred, beta_pred, cohort_alpha_pred, cohort_beta_pred}` and from `entry.latency.{mu, sigma, onset_delta_days, mu_sd, mu_sd_pred, sigma_sd, onset_sd, onset_mu_corr, path_mu, path_sigma, path_onset_delta_days, path_mu_sd, path_mu_sd_pred, path_sigma_sd, path_onset_sd}`. The latency-posterior projection performs the rename described in §3 (`mu → mu_mean`, `sigma → sigma_mean`, `path_mu → path_mu_mean`, etc.). Step 3 ensures `entry.latency` carries the values written by the patch writer; the source ledger is the only writer.

Update `applyPromotion` in `modelVarsResolution.ts:154-210` to write the new `p.posterior` block from the resolved entry's Beta shape and the new `p.latency.posterior` block from the resolved entry's latency block, mirroring the existing `p.forecast` writes at `:174-176`. The behaviour is: if the resolved entry has a Beta shape (alpha and beta both finite and positive), project the full Beta block onto `p.posterior` and stamp `p.posterior.distribution = 'beta'`. If the resolved entry has no Beta (e.g. an analytic source where the moment-match returned `{}` because variance was invalid), clear `p.posterior` so a stale projection from a prior promotion cannot persist. Same rule for `p.latency.posterior`: project from the resolved entry's latency block (renaming as above) when it carries the posterior shape; clear when it doesn't.

**The early-return path needs reworking, not just extending.** Today `applyPromotion` returns at `:161` with `if (!result) return undefined;` *before any writes*. That early-return is correct for "no resolved source ⇒ leave forecast scalars as they are" today, but it is wrong for the new contract "p.posterior reflects the active selector, period" — the function would leave a stale `p.posterior` if the bayesian entry was just dropped from `model_vars` and there is nothing to promote. Step 2's actual change therefore has three parts: (a) when an entry resolves and projects, write `p.posterior` and `p.latency.posterior` from the result; (b) when an entry resolves but the result lacks a Beta or a latency posterior, clear the corresponding surface; (c) when no entry resolves at all (the current `:161` early-return), clear `p.posterior`, clear `p.latency.posterior`, and clear the promoted-scalar surface (set `p.forecast.source = undefined`, leave `p.forecast.mean` and `p.forecast.stdev` untouched per the existing comment about not overwriting upstream values with `undefined` — or reset them to `undefined` only when a prior promotion populated them, tracked via `p.forecast.source != null`). The cleanest implementation: replace the `:161` early-return with an explicit `clearPromotedSurfaces(p)` call that handles all three surfaces uniformly, then return.

This is the load-bearing behavioural change. Once this lands, every promotion-triggering event re-establishes `p.posterior` and `p.latency.posterior` from the selected source — and clears them when no source is selected. The hidden invariant that gives the parity defect today — "stale bayesian Beta survives an analytic pin" — is replaced by the explicit invariant "p.posterior and p.latency.posterior reflect the active selector, period."

Blast radius: every promotion-triggering call site rewrites `p.posterior`. Tests that assert `p.posterior` shape after a fit but before a promotion need re-ordering or amendment. The integration suites (`bayesPatchServiceMerge.integration.test.ts`, `liveEdgeReContextOnDslChange.test.ts`, `perScenarioModelVarsDerivation.test.ts`, `bayesPosteriorRoundtrip.e2e.test.ts`, `cfAndAnalysisDerivationParity.test.ts`, `analysisPrepRecontext.integration.test.ts`) all read α/β off `p.posterior` and assert specific values — they continue to work after the refactor as long as the bayesian writer is updated to put α/β onto `model_vars[bayesian].probability`.

Replace the direct write to `graphEdge.p.posterior` (`:314-378`), the direct write to `graphEdge.p.latency.posterior` (`:383-431`), and the slim `model_vars[bayesian]` upsert (`:435-496`) with a single write that puts the full Beta shape into `model_vars[bayesian].probability`, the full latency posterior into `model_vars[bayesian].latency`, and the bayesian-only metadata into `model_vars[bayesian].fit_diagnostics`. Latency posterior projection follows the same pattern: full lognormal shape into `model_vars[bayesian].latency` (already carries µ/σ/onset/t95/dispersion SDs, see `:461-488`); bayesian-only metadata for the latency posterior into the same `fit_diagnostics` block (or a sibling `fit_diagnostics_latency` if separation aids readability — judgement call at implementation time, the user's principle is satisfied either way).

After upserting the bayesian entry, `applyPatch` calls `applyPromotion(graphEdge.p, graphDoc.model_source_preference)` at `:499` (already in place). With Step 2 in place, `applyPromotion` will project the Beta shape from the active source onto `p.posterior` — bayesian if pinned/gated, analytic otherwise. The bayesian writer no longer touches `p.posterior` directly; promotion is the single owner.

A migration shim handles legacy patch files that already reached IDB before this refactor — they carry the pre-refactor shape and continue to feed `applyPatch` correctly because the slice library on the parameter file is unchanged (the patch file format is the slice library, not the projected `p.posterior`). The patch file shape (`BayesPatchEdge.slices`) does not change.

Blast radius: `bayesPatchService.applyPatch` is rewritten end-to-end; `applyPatchAndCascade` orchestration is preserved. Tests `bayesPatchServiceMerge.integration.test.ts:131-296` (which asserts on `posterior.fitted_at`, `slices['window()'].alpha=43`, `edge.p.posterior.alpha=43, beta=119.5, hdi_lower=0.22, provenance='bayesian'`) and `bayesPosteriorRoundtrip.e2e.test.ts:105-164` need updates for the new entry shape, but their asserted values on `p.posterior` (α, β, provenance) continue to hold after the integrated promotion path runs. Their HDI assertions and `fitted_at` reads must migrate to read from `model_vars[bayesian].fit_diagnostics`.

### Step 7 — BE resolver simplification

### Step 9 — Migration / backwards compatibility

Existing graphs in IDB and parameter files carry the lopsided shape: `p.posterior` with bayesian-fit-specific metadata, `model_vars[bayesian].probability` with only `{mean, stdev}`. After the refactor the new readers tolerate the old shape on read by: the new `model_vars[bayesian].probability` extension is additive — old graphs without the predictive Beta fields and without `fit_diagnostics` are valid; the bayesian Beta still lives on `p.posterior` until `applyPromotion` runs; once promotion runs, `p.posterior` is rewritten from `model_vars[bayesian].probability`, and if that doesn't carry the Beta, the rewrite clears `p.posterior` (correct: the system has lost the Beta, and the promoted view should reflect that).

To avoid the "first promotion clears the Beta" behaviour, an opt-in single-pass migration runs at file load. The migration scans every edge with a `p.posterior` carrying α/β and no `model_vars[bayesian].probability.alpha`, copies α/β (and the rest of the Beta shape) onto `model_vars[bayesian].probability`, copies the bayesian latency posterior fields onto `model_vars[bayesian].latency` (mapping `mu_mean → mu`, etc., the inverse of the §3 promotion rename), and stamps the bayesian-fit metadata onto `model_vars[bayesian].fit_diagnostics`. The migration is idempotent: re-running on a migrated graph is a no-op.

**Persistence is the load-bearing detail, not the migration logic itself.** The existing migration hooks in `workspaceService.ts` (the doc 61 dispersion-field rewrite at `:631` and the manual-source removal at `:634`) run inside the initialisation phase: the comment at `:626-630` records that the rewrite is *deliberately* "absorbed into originalData without marking the file dirty", and the `FileState` at `:663-684` is constructed with `isDirty: false, isInitializing: true, originalData: structuredClone(data)`. Following that pattern for the new migration would mean the migrated shape never persists — every load re-migrates from the un-migrated on-disk content, every save writes the un-migrated shape back (because `originalData` was set to the migrated shape, so the differ sees no change), and share bundles / IDB snapshots stay in the lopsided pre-refactor shape forever. That outcome is acceptable for the doc 61 migration because the rewrite is a field rename inside `posterior` (and the BE accepts both shapes), but it is **not** acceptable for this refactor because (a) the BE resolver's reorder (Step 7) reads `model_vars[promoted_source].probability` first and the source ledger needs to actually carry the Beta on disk for older graphs to behave correctly, and (b) `applyPromotion` after the refactor will *clear* `p.posterior` if `model_vars[bayesian]` does not carry the Beta — re-migrating on every load while never persisting is fine only if the user never closes the tab between fresh fits.

The plan therefore needs a distinct migration mechanism that *does* dirty the file. Recommended approach: add the new migration to `workspaceService.ts` as a sibling to `_migrateDispersionShapeInPlace`, but break out of the `isInitializing` pattern when the migration actually rewrote something — either by setting `isDirty: true` on the constructed `FileState` for migrated files (preserving the migrated shape in `originalData` so subsequent diffs are accurate, and stamping `isDirty: true` to force a save on next user action), or by setting `originalData = structuredClone(unmigratedData)` for migrated files (so the differ sees the migration as a real diff and the user's next save persists it). The first option is cleaner because it does not pretend the migration was a user edit; the second preserves the existing `originalData` semantics. Either works; pick at implementation time. Whichever is chosen, the migration must produce three observable outcomes: (i) the live graph in IDB carries the migrated shape after the load completes; (ii) the next git push includes the migrated shape; (iii) re-loading a migrated file is a no-op (idempotency). A new test (`bayesianMigrationPersistence.test.ts`) pins all three.

A complementary migration also runs against parameter file slices on first read: any slice that carries `n_effective` (and other fields needed by the new `model_vars[bayesian].probability`) is already in the new shape; no parameter-file migration is needed because the bayes patch service is rewritten to populate `model_vars[bayesian].probability` from the slice on every patch apply.

Recommendation: the on-load migration plus explicit dirtying is preferable to "first promotion clears the Beta" because share bundles, CLI snapshots, and IDB-stored graphs that the user has not opened recently will be migrated and persisted on next open without losing diagnostic state. The behavioural contract is: any graph created before the refactor produces the same FE display state after one open-cycle as it did before, with `model_vars[bayesian]` now carrying the bayesian fit's full state and the migrated shape preserved across save/reload.

### Phasing recommendation

Because Step 2 (extend `applyPromotion`) silently changes the writer of `p.posterior` and Step 3 (rewrite bayes patch) changes the field's transient state across event boundaries, the safest sequencing is **atomic in one PR**, with the migration (Step 9), the schema (Step 1), and the promotion-coverage prerequisites (Step 0) included. Step 0 must precede Step 2 in commit order regardless. Phasing into "add new writer alongside old" is awkward because both writers write the same field; a phasing where bayes patch keeps writing `p.posterior` directly while promotion also writes it produces order-dependent state that drifts harder than the current bug.

If atomic is not feasible, a two-commit phasing is acceptable: (a) land Step 0 (gaps) + Step 1 (schema) + Step 3 (writer rewrite) + Step 9 (migration), so the bayesian writer puts the Beta into `model_vars[bayesian].probability` and continues to write `p.posterior` directly using the same Beta, plus the schema is wide enough; readers can begin migrating during this phase but they don't have to. (b) land Step 2 (promotion writes `p.posterior`) + Step 4 (reader migration) + Step 5 (slice contexting reverse) + Step 6 (CF sentinel extension) + Step 7 (resolver reorder) + Step 10 (test pins). Between commits the system is in a "bayesian writer writes everything; analytic pin still produces the parity defect" state — the user's bug is not yet fixed but no regression is introduced. The atomic version fixes the bug at the same commit as the architecture cleanup; the two-commit version delays the fix by one cycle.

Recommendation: atomic, one PR. The blast radius is large but bounded; the refactor is mechanical once the type shapes are settled; deferring the user-visible fix is a worse trade.

## 7. Persistence and migration strategy

The plan recommends an explicit on-load migration in `workspaceService.ts` placed alongside the doc 61 `mu_sd_epist` → `mu_sd` rewrite at `:631` and the manual-source removal at `:634`, but **outside** the `isInitializing: true / isDirty: false` window the existing migrations sit inside (see §4 Step 9 for the persistence-mechanism detail). The migration: for every edge with `p.posterior.alpha != null` and either no `model_vars[bayesian].probability.alpha` or stale `model_vars[bayesian].probability` (which today contains only `{mean, stdev}`), copy the full Beta shape onto `model_vars[bayesian].probability` (mapping `window_n_effective` → `n_effective`), copy the bayesian latency fields onto `model_vars[bayesian].latency` (mapping `mu_mean → mu`, etc.), and copy the bayesian-fit metadata onto `model_vars[bayesian].fit_diagnostics`. Derive `gate_passed` from the existing logic (`meetsQualityGate` semantics — already in `bayesPatchService` at `:437-441` and `posteriorSliceContexting`). When the migration actually rewrites an edge, the constructed `FileState` is marked dirty (or `originalData` is set to the un-migrated input — see Step 9 for the two implementation options) so the migrated shape persists on next save. Idempotent: re-run on a migrated graph is a no-op.

Parameter files do not need migration because the patch service is rewritten to populate `model_vars[bayesian].probability` from slices on every patch apply; the slice library on the parameter file is already in the right shape.

Share bundles and CLI snapshots are graphs serialised into JSON. They flow through the same load path on the FE and through `cloneGraphWithoutBayesRuntimeFields` on the CLI; the migration runs once on first load. The CLI's `analyse` command may need an explicit migration step in its load path because it bypasses `workspaceService` — confirm at implementation time and add the migration there if needed. As a safer alternative, the CLI's `materialiseScenarioFeTopo` (or the equivalent Python hook for analyse-prep) can call `applyPromotion` over each edge after building the request graph; this both runs the migration (by virtue of promotion clearing/rewriting `p.posterior`) and produces a request graph that the BE can read uniformly.

The git-commit boundary requires no special handling beyond Step 9's persistence mechanism: when the migration dirties the file (or sets `originalData` to the un-migrated shape so the differ sees a real diff), the new shape is what's committed on next push. Without that mechanism the on-disk shape stays lopsided; with it, the next save normalises the on-disk shape across the entire workspace.

## 9. Risks and open questions

**HDI fields**. The plan moves `hdi_lower`, `hdi_upper`, `hdi_lower_pred`, `hdi_upper_pred`, `cohort_hdi_*`, `hdi_level` off `p.posterior` and onto `fit_diagnostics`. The clean alternative is to compute them on the fly from α/β when displayed (closed-form Beta quantiles); HDI is a deterministic function of α and β. If the alternative is preferred, the fields stay off `p.posterior` permanently and the display surfaces compute them. The plan's choice (move to fit_diagnostics) is conservative and preserves bayesian-specific computation paths (the MCMC HDI is more accurate than analytic-quantile HDI for skewed posteriors with low concentration). Recommendation: move to fit_diagnostics now; leave the closed-form computation as a follow-up if a future analytic surface needs HDI bands.

**`window_n_effective` vs `n_effective`**. The current `ProbabilityPosterior` carries `window_n_effective` and `cohort_n_effective`; `ModelVarsProbability` carries `n_effective` and `cohort_n_effective`. The plan unifies on the `model_vars` naming: `n_effective` for the window family, `cohort_n_effective` for the cohort family. The patch writer maps `windowSlice.n_effective` → `model_vars[bayesian].probability.n_effective`, which propagates through promotion to `p.posterior.n_effective`. The BE resolver's read at `model_resolver.py:491-495` keys on `cohort_n_effective` and `window_n_effective` — change to `cohort_n_effective` and `n_effective`. Watch for any consumer that grep's for `window_n_effective` specifically.

**`provenance` semantics**. Today, `p.posterior.provenance` is whatever the bayesian fit's worker recorded (`'bayesian'`, `'pooled-fallback'`, `'point-estimate'`, `'skipped'`). After the refactor, `p.posterior.provenance` reflects the active source's provenance, which for analytic is `'analytic_window_baseline'` or `'analytic_cohort_baseline'`, and for bayesian is the worker's `windowSlice.provenance`. UI labels that read this field need to handle both vocabularies. `PosteriorIndicator.tsx:235, 465` displays the value verbatim and so handles both. Full vocabulary in §6.6.

**CLI graph snapshot path**. The CLI's `analyse` command builds graph snapshots that bypass the FE's load-time migration. If the CLI receives a pre-refactor-shaped graph (lopsided `p.posterior` carrying bayesian metadata, slim `model_vars[bayesian]`), the BE resolver's reorder (`model_vars` first, `p.posterior` second) helps mask the issue but is not bulletproof — the analytic pin scenario can still hit the parity defect on the CLI. Either run the on-load migration in the CLI's graph loader, or run `applyPromotion` over the graph before submitting. The latter is cleaner because it's the same code path the FE uses; recommend extending `materialiseScenarioFeTopo` (or its equivalent CLI hook) to call promotion explicitly after building the request graph.

**Pre-refactor IDB graphs**. After the refactor lands, any IDB graph with the old shape needs a single FE open to migrate. Users with multiple un-opened graphs in IDB will have those graphs migrate as they open them. No action required — the migration is idempotent and gentle.

**Bayes patch backward compatibility**. The patch file format (`BayesPatchEdge.slices`) does not change. Patch files written before the refactor remain applicable after. Patch files written after the refactor against pre-refactor graphs work because the new patch service is written to update both the new model_vars shape and trigger promotion.

**Conditional probability mirror — DECISION REQUIRED**. Each `conditional_p[X].p` mirrors `edge.p` and carries its own `posterior`. Every step of the plan applies to the conditional p block as well. The slice-contexting helper already mirrors under each conditional (`posteriorSliceContexting.ts:174-180, 307`); the bayes patch service does NOT — only `edge.p` is patched today. This is a pre-existing asymmetry. After the refactor, patching produces an `edge.p` whose `model_vars[bayesian]` is updated and whose `p.posterior` is rewritten by promotion, but the conditional p blocks' `model_vars[bayesian]` and `p.posterior` are stale until the next contexting pass. For most users this is invisible because the contexting pass runs frequently (DSL changes, file syncs), but it can present as a stale conditional posterior in narrow timing windows. Recommendation: extend the bayes patch service to mirror under conditional p blocks at the same point as the edge.p update (`bayesPatchService.ts:498-499`). The fix is small (a loop over `graphEdge.conditional_p ?? []`) and aligns the patch service with the slice contexting helper. If this is deferred, document the asymmetry as a known issue and add a regression test that pins the pre-refactor behaviour so it does not silently change.

**Layer-1 selector preference at the parameter-file level**. Today the parameter file does not carry a selector preference. A pre-refactor IDB graph carrying analytic pin + stale bayesian Beta on `p.posterior` is the failure mode. After the refactor, on first open, the migration normalises `model_vars[bayesian]`, then the next promotion-triggering event rewrites `p.posterior` from the analytic source. The test in §4 Step 10 pins this exact reproducer.

**Promotion gates that fail silently**. Step 0 catches the six known sites where mutations bypass promotion. There may be additional sites that future code introduces. The new test `promotionCoverageInvariant.test.ts` defends against regressions by walking the call graph statically (or by mocking `applyPromotion` in a representative integration scenario) and asserting that every model_vars or source_preference mutation is paired with promotion. This test should be added in Step 0 and run on every PR.
