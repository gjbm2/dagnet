# Local Postgres for Snapshot DB (Dev)

**Status:** active · **Last reviewed:** 27-May-26

Run the snapshot DB against a **local Postgres** instead of the production
Neon database during development. This is faster (no serverless cold-start,
no London round-trip, no SSL handshake) and — more importantly — keeps
synthetic data generated by `bayes/synth_gen.py` out of the production
database entirely.

Everything below is **idempotent**: every step is safe to re-run, and the
per-session start is wired into `dev-start.sh` so the local cluster comes up
with the rest of the dev environment.

---

## 1. Background: how the connection is wired today

There is a single configuration point — `DB_CONNECTION` in
`graph-editor/.env.local`. Both sides read it:

| Consumer | Reads `DB_CONNECTION` from |
|---|---|
| **Writer** — synth gen (`write_to_snapshot_db`) | `graph-editor/.env.local` directly, via `_load_db_connection()` in `bayes/synth_gen.py` |
| **Reader** — backend (`snapshot_service._get_pool`) | process env `os.environ['DB_CONNECTION']` (`dev-start.sh` exports it into the Python pane) |
| **Tests** — `bayes/test_harness.py` | `graph-editor/.env.local` |

Driver is plain **`psycopg2`** with no ORM, so a local Postgres is
wire-identical to Neon: **no application code changes are needed**. Switching
between Neon and local is one line in `.env.local`.

Production is **Neon serverless Postgres** (eu-west-2 / London, pooled
endpoint, `sslmode=require` + `channel_binding`).

---

## 2. Prerequisites

- WSL2 / Ubuntu (this guide targets that; macOS notes are inline where they
  differ).
- The repo's existing dev setup already done (`./dev-bootstrap.sh` or
  `./dev-start.sh` at least once).

## 3. One-time setup

### 3.1 Install Postgres (idempotent)

```bash
# Installs only if not already present.
command -v psql >/dev/null 2>&1 || { sudo apt-get update && sudo apt-get install -y postgresql postgresql-client; }
```

> macOS: `brew install postgresql@16 && brew services start postgresql@16`.

### 3.2 Start the cluster (idempotent)

WSL2 does **not** run systemd by default, so use the `service` command, not
`systemctl`. `pg_isready` makes this safe to re-run:

```bash
pg_isready -q || sudo service postgresql start
```

### 3.3 Create the role and database (idempotent)

We use a dedicated role `dagnet` / database `dagnet_snapshots` so the
connection string is explicit and self-contained. The guards below mean
re-running is a no-op:

```bash
# Role (idempotent: only created if absent)
sudo -u postgres psql -tAc "SELECT 1 FROM pg_roles WHERE rolname='dagnet'" | grep -q 1 \
  || sudo -u postgres psql -c "CREATE ROLE dagnet LOGIN PASSWORD 'dagnet';"

# Database owned by that role (idempotent)
sudo -u postgres psql -tAc "SELECT 1 FROM pg_database WHERE datname='dagnet_snapshots'" | grep -q 1 \
  || sudo -u postgres createdb -O dagnet dagnet_snapshots
```

### 3.4 Schema (created automatically — nothing to do)

The schema provisions itself. `ensure_schema()` in
`graph-editor/lib/snapshot_service.py` is the single source of truth and
creates both tables (`snapshots`, `signature_registry`) and their indexes
idempotently on first DB access:

- the **backend** runs it when its connection pool is first created — i.e. on
  the first snapshot read/write after the Python server starts;
- **synth gen** runs it before its first write, so a synth run against an
  empty local database provisions the schema itself.

So the first backend start *or* synth-gen run against the empty
`dagnet_snapshots` database creates everything. There is no manual DDL load or
migration step. (This was previously a defect — the core `snapshots` table was
created by no code path; see the project history for the fix.)

To pre-create the schema manually (optional), invoke `ensure_schema` directly:

```bash
. graph-editor/venv/bin/activate
DB_CONNECTION="postgresql://dagnet:dagnet@localhost:5432/dagnet_snapshots" \
  python -c "import sys, os, psycopg2; sys.path.insert(0,'graph-editor/lib'); import snapshot_service as s; c=psycopg2.connect(os.environ['DB_CONNECTION']); cur=c.cursor(); s.ensure_schema(cur); c.commit(); print('schema ensured')"
```

### 3.5 Point `.env.local` at the local DB

Edit `graph-editor/.env.local`. Keep the Neon URL commented so you can switch
back instantly:

```bash
# Production (Neon) — uncomment to switch back:
# DB_CONNECTION=postgresql://neondb_owner:...@...neon.tech/neondb?sslmode=require&channel_binding=require

DB_CONNECTION=postgresql://dagnet:dagnet@localhost:5432/dagnet_snapshots
VITE_SNAPSHOTS_ENABLED=true
```

> `localhost`/`127.0.0.1` in the URL is also the signal `dev-start.sh` uses to
> decide whether to auto-start the local cluster (see §4).

## 4. Auto-start with `dev-start.sh`

So the local cluster comes up automatically with the dev environment, the
start scripts call a small idempotent helper, **`scripts/ensure-local-postgres.sh`**,
which:

1. Returns immediately (no-op) unless `DB_CONNECTION` points at
   `localhost`/`127.0.0.1` — so Neon users are unaffected.
2. Runs `pg_isready`; if the cluster is down, runs `sudo service postgresql start`.
3. Ensures the role and `dagnet_snapshots` database exist (the §3.3 guards).

It does **not** create the schema — that happens automatically on first DB
access (see §3.4).

`dev-start.sh` invokes it just after it loads `.env.local` (around the
`export $(grep ... DB_CONNECTION ...)` block), before the tmux panes launch.
The call is guarded so a missing/failed start never aborts `dev-start.sh`
(`set -e`–safe):

```bash
# Ensure local snapshot Postgres is up (no-op unless DB_CONNECTION is local)
DB_CONNECTION="${DB_CONNECTION}" bash "${ROOT_DIR}/scripts/ensure-local-postgres.sh" || true
```

`dev-restart.sh` and `dev-stop.sh` need no changes: the local cluster is a
host service independent of the tmux session, and is left running between
restarts.

---

## 5. Verify

```bash
LOCAL_URL="postgresql://dagnet:dagnet@localhost:5432/dagnet_snapshots"

pg_isready                                            # accepting connections?
psql "$LOCAL_URL" -c "\dt"                            # snapshots + signature_registry present?
curl -s http://localhost:9000/api/snapshots/health    # {"status":"ok","database":"connected"}
```

Then run a synth-gen job and confirm rows land locally rather than in Neon.

---

## 6. Switching back to Neon

Re-comment the local line in `.env.local`, uncomment the Neon line, restart
the dev servers (`Ctrl+B` then `R`, or `./dev-stop.sh && ./dev-start.sh`).
Nothing else to undo — the local cluster keeps its data for next time.

## 7. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `psql: could not connect to server` | Cluster not started — `sudo service postgresql start`. WSL2 has no systemd by default, so `systemctl` won't work; use `service`. |
| `FATAL: role "dagnet" does not exist` | Re-run §3.3. |
| `relation "snapshots" does not exist` | Should not happen — the schema auto-creates on first DB access (§3.4). If it appears, `ensure_schema()` failed (check the server/synth logs) or the `dagnet` role lacks CREATE privilege on the database. |
| `peer authentication failed` | You connected over a Unix socket as the wrong OS user. Use the TCP URL (`@localhost:5432`) with password auth as in §3.5. |
| Port 5432 already in use | Another Postgres (e.g. a monorepo instance on 5433) is unrelated; pick a free port and update both the cluster config and the URL consistently. |
| Rows still appearing in Neon | `.env.local` still points at Neon, or the Python server wasn't restarted after the edit. Restart the servers. |
